# Platform readiness — October 17, 2026

Geek Protocol is a Kaspa onboarding ecosystem built for Proof of Learning. A.C.E. is part of the intended product, alongside learning, gameplay and carefully governed rewards. The founder requested page/link metadata updates, two essential additions and five system improvements, and reported passkey creation failing in Amazon Silk on a family Fire tablet. This record separates the present candidate from proposed infrastructure.

## Current candidate

- **SEO-001:** one maintained [page catalog](site-pages.json) generates titles, descriptions, canonical URLs, favicons, Open Graph and Twitter cards, with actual image dimensions. It covers all 30 public HTML pages and ten private operator templates. Generic account shells contain no player data; private templates remain noindex/nofollow. Sign-in and the player dashboard are excluded from search indexing. The sitemap has 27 indexable pages; robots excludes API/operator routes. The existing Organization JSON-LD and CSP hash remain unchanged.
- `npm run site:write` updates metadata; `npm run site:check` rejects missing page records, drift, missing images, broken local targets/fragments and stale sitemap/robots. The check is part of full verification and GitHub CI. It adds no browser script, network call or tracking. All 863 static internal links/fragments pass. An unnecessary homepage preconnect is removed and the practice source link explicitly includes noopener.
- **External links:** [dated read-only audit](site-link-review-2026-10-17.json) checked 77 distinct public external URLs: 66 returned HTTP 2xx/3xx to HEAD; eleven were blocked, timed out or returned a gateway error. Those eleven are unverified, not established dead links, and are preserved. This does not audit every question-bank citation or dynamic JavaScript destination. The audit contains public URLs only.
- **AUTH-002:** bounded, local platform-authenticator detection and device help supplement basic WebAuthn API detection. A negative result does not disable external authenticators or cross-device passkeys. Failure messages distinguish unsupported authenticators and duplicate credentials; they do not replace a player or clear progress. Changing a Fire tablet browser alone is not promised to add a credential manager. No server authentication rule or recovery method is bypassed. A Fire tablet cannot be made to create a native passkey by website code when the required provider is absent. The installed Silk/Fire OS versions and actual root cause remain unverified; synthetic tests are not device acceptance.
- **CHAIN-003:** the GEEKT desk displays exact token amounts from integer strings and validated decimals, including 1 GEEKT = 100000000 base units at eight decimals. Unknown metadata never becomes a guessed wallet amount. Configured, queued, sent and indexed states remain distinct. The change creates no signer, automatic send or Mainnet payment.

## Two essential additions

1. **A working account path across the intended devices (AUTH-003).** Design parent-approved device pairing or a parent-controlled recovery method alongside passkeys. A supported, freshly authenticated device should explicitly approve a short-lived one-use tablet link, bound to the intended player and destination device. Require expiry, rate limits, replay prevention, device revocation and clear separation of existing guest progress. Never use a name or address alone as proof. Define parent/child account relationships before claiming family-account support. The new compatibility help is available in this candidate; device pairing and email recovery are not implemented.
2. **A complete GEEKT reward rehearsal (CHAIN-001).** The asset and manual receipt desk already exist. Complete one eligible Daily, queue its receipt within the existing five-minute window, export the exact amount/recipient/network, approve one TN10 transfer in the wallet, attach the reveal hash and reconcile that same hash. Record recipient balance evidence privately. Only then specify an optional wallet-connected sender or bounded worker. A configured flag, test balance, synthetic transfer fixture or formatted amount is not an end-to-end reward receipt. No new Mainnet signer or automated settlement is approved by this work.

## Measured source baseline and limits

A single local Node 24 process on October 17 loaded 600 active Kaspa questions in approximately 8.7 ms; evaluating readiness across 8,205 active questions took approximately 74.5 ms cold and 0.03 ms for the warm result clone. All active/retired question JSON totals 9,445,483 bytes; process RSS after this work was approximately 97 MB. These figures describe one development process, not production cold-start time, concurrency, a user limit or load-test acceptance. Category banks and readiness already have process-local caches. More questions alone do not justify an immediate database cutover.

A.C.E. currently uses authored, source-linked Study guidance and a simulated Duel opponent. There is no generative tutor, model gateway, durable agent runtime or autonomous protocol operator in the inspected package graph. A.C.E.'s next implementation should have a reviewed model/runtime choice and credential provisioning, a separate evaluation set, a narrow tool policy and a small controlled pilot. No model API key, billable provider or new cloud resource was provisioned by this work.
