## Account access

`/sign-in/` offers discoverable passkeys with user verification required. Depending on the authenticator, this may use fingerprint, face or a device PIN; it is not a guarantee of biometrics on every device. The server uses integrity-locked `@simplewebauthn/server` 14.0.3 to verify registration and assertions. Origin, RP ID, user handle, signature, verification flag and counters are checked. Five-minute challenges are bound to the requesting player/session and consumed once. Login and registration rotate cookies and atomically preserve player identity. Database corruption fails closed.

New guest players may establish their first passkey. Existing passkey accounts require fresh passkey proof to manage credentials. Wallet-linked players can authorize enrollment using an explicit KIP-5 **AUTHORIZE PASSKEY ACCOUNT ACCESS** message. Linking a wallet to a passkey-only player or recovering a wallet changes the wallet identity version and invalidates old passkeys and passkey sessions; re-enrollment after recovery starts a new passkey set rather than reactivating old credentials. Removing a credential invalidates passkey sessions for that account. Wallet signatures remain required by the existing payout-authorization protocol.

Keep another saved/synced passkey, another authenticator or a linked wallet. Geek has no help-desk bypass for an account with no remaining recovery credential. A passkey sync provider may provide its own recovery; Geek cannot guarantee it. Production RP ID is `geekprotocol.xyz`, with exact bare/www origins. A preview needs an exact `PASSKEY_ORIGIN`; its credentials are separate. Local HTTP is restricted to explicitly configured localhost outside production.

## Wallet lab

`/wallet-lab/` creates only testnet-10 wallets. No signing, sending, Mainnet address creation, seed-import endpoint or wallet reward bonus is enabled. The separate `wallet.geekprotocol.xyz` product remains read-only. Mainnet keys should not be introduced into this lab.

The lab uses the existing integrity-pinned `@dfns/kaspa-wasm` 0.14.1 SDK for randomness, BIP39 validation, BIP32 derivation and address encoding. Its generated Node loader is adapted only for asynchronous browser WASM loading by `scripts/build-wallet-sdk.mjs`. SDK code and WASM are regenerated by `npm test` and the Vercel build, with the upstream ISC license copied alongside them. SDK WASM SHA-256: `976932dc84870ef789fbd2697428da0da5c1ac191dfed4b165eb305875b0fe71`. First receive path: `m/44'/111111'/0'/0/0`. Tests compare the adapted SDK with the unmodified package.

Wallet material is encrypted locally with AES-256-GCM, random salt/nonce and PBKDF2-SHA256 (600,000 iterations), with authenticated format/network/path/address parameters. Passwords are 12–256 characters. This is a selected testnet design, not a wallet audit. Browser storage is encrypted ciphertext only. A new wallet requires confirmation of three recovery words, an encrypted-backup download and successful re-import/password/address verification before local persistence. A recovery phrase is generated and shown locally; it is never sent to HQ. No existing recovery phrase is accepted by a login form. Imported files are bounded encrypted Geek testnet backups only.

The page loads no analytics or third-party scripts and has an additional restrictive CSP. The base CSP permits WebAssembly compilation with wasm-unsafe-eval while keeping JavaScript eval and inline scripts disallowed. Secrets clear from the interface on hiding/navigation and after three minutes. JavaScript strings and browser memory are not guaranteed securely erased; password strength, XSS/origin compromise, device compromise, downloads and backup custody remain review topics. Geek account passkeys do not decrypt this vault. Biometric wallet unlock needs a separate reviewed key-wrapping/recovery design, not a reuse of a WebAuthn signature as a Kaspa private key.

## Reward and pilot boundaries

Testnet transfer amounts are formatted using integer base units and the receipt's validated decimals. The exact raw amount remains in the exported transfer instruction. Copy controls do not submit a transaction. “Indexed confirmed” remains a matching operation observed at a particular check, not independent finality proof. Ambiguous results require investigation of the same hash before any new send. Daily limits and proof expiry are unchanged.

`docs/pilots/wallet-safety-v1.json` is a prepared course, not permission to recruit. Assessments need instructor approval and do not yet cover every objective. `npm run pilot:evaluate -- /private/path/pilot.json` reads coordinator-supplied observations, rejects invalid scores/order/early delayed observations, counts missing follow-ups explicitly and computes paired changes only for observed pairs. It does not authenticate scores or authorize rewards. Keep learner data and consent records out of the public repository.

Primary implementation guidance: [WebAuthn](https://www.w3.org/TR/webauthn-3/), [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server), [Kaspa Wallet API](https://docs.kaspa.org/integrate/wallet). KasWare's [August 6 biometric release](https://github.com/kasware-wallet/kasware-app/releases/tag/v0.5.1) establishes the requested UX precedent; it is not an HQ compatibility test.
